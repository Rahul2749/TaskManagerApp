# Regression checks

Run from the repository root with the .NET 10 SDK:

```powershell
dotnet run --project tests/TaskManager.RegressionTests/TaskManager.RegressionTests.csproj
```

The console runner exits with 0 when all groups pass and 1 on failure. It prints each group and a final assertion count. No production configuration, credentials or data are required.

Coverage includes controller ownership boundaries, authorization metadata, task editing and dates, assignment validation, template limits/content, due-soon quotas, threaded comment deletion, custom-field duplicates, subscription retries, browser dropdown refresh/reopen/failure/race cases and mobile editor field preservation/races. Billing checks cover checkout signatures, workspace isolation, trial activation, entitlement cache invalidation, signup provider transitions, verified legacy provider recovery, missing callback recovery, stale reconciliation rejection, billing retry states and pricing callback submission.

Controller checks use EF Core InMemory. PostgreSQL queries are translated without opening a database connection; the relational billing atomic update path is not executed by this runner. Razorpay checks use mocked HTTP responses and test-only secrets, with no provider account access or charges. Mobile checks compile the actual viewmodel and MVVM generators with minimal navigation/attribute shims; they do not replace an Android build or UI test. Browser component checks invoke its event/load methods without rendering.

UI performance regressions also cover duplicate login submissions, navigation without document reload, lightweight JWT role/expiry parsing, concurrent storage reads without persistent token caching, and notification responses after logout. Run `node tests/ui-performance.spec.cjs` for gateway loading/retry and startup source checks, and `python tests/test_http2_config.py` for the isolated Nginx configuration helper checks. See `docs/UI_PERFORMANCE_2026-10-11.md` for measurements and deployment verification.

Login navigation checks exercise the actual client authentication service using tokens generated by the server TokenService and isolated HTTP/storage fakes. They cover immediate authentication publication, stale startup reads, each role's dashboard, onboarding, authentication-page return URL rejection, valid application return URLs, and missing-user errors.

Session race checks delay an older user lookup and expired-token cleanup across a new login. They verify that stale reads cannot replace the new user and cleanup cannot delete the newly persisted session.

Dashboard checks cover empty projects/workspaces, completion rounding, tenant/manager scope, project collections, and UI failure/retry recovery. The shared counts projection is translated with Npgsql to verify SQL contains no division and retains filtering/analytics limits. These translation checks do not open a PostgreSQL connection.

Rendering checks use HtmlRenderer and the actual notification/table components to verify isolated badge updates, subscription disposal, bounded rows, later pages and changed records. Initialization checks verify independent task-detail/integration reads overlap and preserve data. These are component regressions, not browser timing or layout tests. After a Release publish, run `node tests/verify_blazor_publish.cjs output/net10-ui-publish` to verify the .NET 10 SDK's fingerprinting, caching, inline boot configuration and Brotli asset endpoints.
