# Bug review and fixes — 11 October 2026

The initial list was shared before changes. The review covered task and project APIs, related task features, validation, templates, automation jobs, browser authentication and subscription state, and the mobile task editor. The earlier project dropdown fix remains in place.

## Findings

All 22 findings below have source fixes. Findings 16–18 were found during implementation and dependency validation. Finding 19 was reported afterward and handled first as the highest priority. Findings 20–22 cover the subsequent checkout and billing reports.

### Payment follow-up: verification 400 and synchronization 503 (#22)

**Confirmed cause; source fixed and affected VPS provider labels repaired.** Signup creates a subscription with `Provider = internal`. Checkout updated the existing subscription's plan and Razorpay IDs but left that provider label unchanged. Verification then rejected the callback with 400, and synchronization returned 503 before attempting a provider request. The separate temporary socket failure during checkout was followed by a successful Razorpay request; it does not explain the repeated fast synchronization failures.

The VPS was running commit `a47ae6e5411bef5498abdd4bed42da34d2ebe06a`. Both stored provider subscriptions still had the `internal` label. Authenticated Razorpay API reads using the running server's Test Mode credentials confirmed the exact stored IDs and `authenticated` status with future subscription start dates. After those checks, a guarded transaction changed only `Provider` to `razorpay` and the update timestamp for organizations 1 and 2. Status, plan and access dates were not manually changed. The currently deployed **Refresh billing** endpoint can now reconcile those records normally; its displayed result still needs confirmation in the user's logged-in browser.

Checkout now saves the provider name when replacing a signup subscription. Verification and synchronization also recover legacy `internal` records with stored Razorpay subscription IDs, correcting the label only after a successful authoritative provider read. Callback signatures and organization/subscription matching remain required. Atomic reconciliation additionally checks the previous provider label alongside the subscription ID and timestamp. Arbitrary provider labels remain rejected. Deploy this follow-up source fix to prevent recurrence for other signups.

The new checkout regression reproduced the missing provider transition before the fix. Additional checks cover legacy recovery, invalid signatures, provider failures, unrelated providers and malformed IDs.

### Payment follow-up: successful test checkout without plan access (#20–21)

**Resolved in source; deployment and account reconciliation remain necessary.** The screenshot shows Razorpay Test Mode, a refundable ₹5 authorization transaction and a ₹149 monthly subscription. The app schedules paid subscriptions after a 14-day trial. Its checkout handler received payment ID, subscription ID and signature, but discarded all three and displayed a generic success message. The server persisted `incomplete` and relied exclusively on webhooks to activate access.

[Razorpay's test guide](https://razorpay.com/docs/payments/subscriptions/test/) explains that future-start test subscriptions can remain `authenticated` after the ₹5 authorization without emitting activation webhooks. This is a matching failure path, not proof of the exact provider state of this workspace. The deployed public `/api/billing/status` endpoint returned `configured: true` and `webhookConfigured: true` during the investigation; this confirms configuration presence, not successful event delivery.

The browser now sends the result to `POST /api/billing/verify-checkout`. The server checks the subscription belongs to the current organization, verifies HMAC-SHA256 using the API key secret and the stored subscription ID, then fetches the subscription from Razorpay. An authenticated subscription within its trial grants trial access; a provider-active subscription grants active access. Created, expired and canceled subscriptions do not gain paid access. Successful writes invalidate cached entitlements. Relational writes check the subscription ID and previous update timestamp atomically so an old provider read cannot overwrite a newer checkout or webhook.

Billing now calls `POST /api/billing/sync` on entry and through **Refresh billing**. This reads the existing provider subscription and recovers missing confirmations without charging, recreating or canceling a subscription. Both endpoints require OrganizationAdmin and a workspace ID. Provider/network failures preserve stored access and return retry guidance. The browser reports an activation success only after confirmation.

Billing requests have time limits, subscription/invoice failures are displayed accurately, and the page offers retry instead of silently classifying a failed subscription load as Free. The screenshot's loading placeholders alone do not establish which network request was slow or failed.

After deploying both server and browser client, sign in as the workspace's organization admin and open **Billing → Refresh billing**. If Razorpay reports the existing subscription authenticated with a future trial end, it will become Trial with the selected plan's access. Do not repeat checkout to recover this authorization. Test Mode does not establish a live payment; live billing requires matching live keys, plans and webhook configuration. The later #22 investigation repaired the two verified VPS provider labels described above; no provider charge, cancellation or new subscription was performed.

Implementation follows [Razorpay's subscription verification guide](https://razorpay.com/docs/payments/subscriptions/integration-guide/).

The subsequent Razorpay dashboard screenshot shows the enabled Test Mode webhook still targeting `https://taskmanager-app-plt1.onrender.com/api/billing/webhook`. The current deployment notes identify `https://taskmanager.shape2real.in` as the app hostname. Update the existing webhook to `https://taskmanager.shape2real.in/api/billing/webhook` and ensure its secret matches the running server's `Razorpay:WebhookSecret`. If Render uses another database or no longer serves this deployment, events delivered there cannot activate this workspace. The screenshot shows 10 selected events but not their names; confirm `subscription.authenticated`, `subscription.activated` and `subscription.charged` are included, along with lifecycle and invoice events handled by the controller. This external setting has not been edited by Codex. Changing its URL does not itself establish that an earlier authorization has been reconciled; use the deployed Billing sync fix to recover existing state. See [Razorpay's webhook editing instructions](https://razorpay.com/docs/webhooks/setup-edit-payments/).

### Highest priority follow-up: missing users in Assign To (#19)

**Resolved in source.** The task form cleared `availableUsers` on close but did not restore it on reopening. Opening the form refreshed projects only, leaving newly created users out of the cached user list. Clearing the selected project also emptied the assignee list.

Create and edit now refresh projects and active workspace users together before opening. The form restores workspace users on every open and when the project is cleared; selecting a project still includes users without existing project mappings. Failed refreshes keep the last successfully loaded list and show an error, and the next open retries. Organization and role restrictions still apply.

The new regression reproduced the missing newly created user before the fix. It now covers new users before project selection, close/reopen, projects without mappings, clearing the project, fresh edit options, and refresh failure/retry. Main file: `TaskManager.Client/Pages/Manager/ManageTasks.razor`.

## Validation

The regression runner is `tests/TaskManager.RegressionTests`. Run it from the repository root:

```powershell
dotnet run --project tests/TaskManager.RegressionTests/TaskManager.RegressionTests.csproj
```

It uses the actual controllers with an isolated EF Core in-memory database, real authorization policy evaluation for custom-field endpoint metadata, browser component methods for dropdown loading, PostgreSQL SQL translation without connecting to a server, and linked production mobile viewmodels with UI/navigation shims. Test data includes two organizations, multiple managers, users with different assignments, inactive users and out-of-order responses.

Final regression results: **25 groups passed, 158 assertions, zero failures**, including the original browser dropdown failure, newly created users and reopened dialogs, out-of-order member requests, checkout signature checks, workspace callback isolation, trial activation and cache invalidation, signup provider transitions, legacy provider recovery, missing-confirmation recovery, stale reconciliation rejection, billing retries, pricing callback submission and PostgreSQL query translation. The follow-up incremental web build passed with zero warnings and zero errors.

The web server/client build passed with zero errors and 20 existing MudBlazor analyzer warnings. After the highest priority assignee fix, the regression run rebuilt the browser client successfully with those warnings, and the subsequent incremental server/client build passed with zero warnings and zero errors. The Android build passed with zero errors and five existing warnings about obsolete UI APIs and an unused exception variable. The original Android output directory could not be cleaned because OneDrive denied access; the successful build used a fresh intermediate/output directory:

```powershell
dotnet build src/TaskManager/TaskManager.Mobile/TaskManager.Mobile.csproj -f net10.0-android --no-restore -v quiet -p:IntermediateOutputPath=obj/bug-audit/net10.0-android/ -p:OutputPath=bin/bug-audit/net10.0-android/
```

`git diff --check -- src tests` passed for the source/test changes. Pre-existing guide and deployment document edits were preserved.

## Practical limits

The regression runner uses isolated data and mocked Razorpay responses with test-only secrets. The separate #22 VPS investigation read real subscription metadata, made authenticated subscription status reads against Razorpay Test Mode, and repaired two verified provider labels in PostgreSQL. It did not charge, cancel or create provider subscriptions. No logged-in browser session was connected for final Billing display verification. The runner does not render browser pages or run an Android emulator. EF in-memory checks do not prove relational transaction behavior, the controller's PostgreSQL atomic update path or concurrent request correctness. Existing completed dates and other invalid stored records are not backfilled by these source fixes. This review does not claim the project has no remaining bugs.

Deploy the updated server and browser client to apply API, validation and job scheduling changes. Rebuild the mobile app to apply editor fixes. No schema migration was added by this review.
